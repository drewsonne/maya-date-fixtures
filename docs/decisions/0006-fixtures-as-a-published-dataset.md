# 0006. Test vectors are published as a standalone, citable, language-agnostic dataset

- Status: accepted
- Date: 2026-09-13
- Accepted: 2026-09-13
- Depends on: 0002

## Context

The correctness suite was originally conceived as `docs/fixtures/` inside a single repository. 0002 keeps the packages separate, which forces the question: where do shared test vectors live when four repositories need them?

Copying them into each repository is the answer that must not be chosen. Divergent copies of the same expected values, drifting independently, is precisely the duplication this project spent five ADRs removing — and it would be duplication of the one thing whose correctness the entire project rests on.

There is a better answer than "put them somewhere convenient." Verified, cited Long Count ↔ Calendar Round ↔ day-number ↔ western-date vectors are not an implementation detail of this project. They are a reusable artifact: any implementation in any language can test against them, and a researcher can check them without running code at all. Nothing comparable appears to be published in a machine-readable, citation-bearing form.

That makes the dataset the most externally valuable output of the project, and the only part of it an epigrapher could use and cite without touching JavaScript.

## Decision

Test vectors live in their own repository and are published as `@drewsonne/maya-date-fixtures`, consumed as a development dependency by every other package.

The data is **language-agnostic by construction**: YAML source files carrying no JavaScript, no test framework, and no assumptions about how they will be loaded. The npm package is a distribution channel, not the format. A Python or Rust implementation consumes the same files from the repository directly.

Every record carries its provenance and citation, per the rules in the `maya-fixtures` skill: `attested` values cited to author, year, and page or table; `derived` values with the derivation shown; `unverified` values flagged and excluded from any trust gate. A value generated by running an implementation is not admissible at any provenance level.

The repository is released with versioned tags and archived for citation, so a paper or a downstream implementation can reference an exact version of the dataset rather than a moving branch.

## Consequences

**Easier.** One authoritative set of expected values for four packages, with no possibility of divergent copies. Differential testing between the app's embedded implementation and the library (the open risk in 0005) runs against a shared reference rather than either implementation's own idea of correct. Other implementations, in any language, gain a conformance suite. The project acquires something genuinely citable, which matters for the academic conversation it is meant to support.

**Harder.** Adding a fixture becomes a release: change the dataset, publish, bump four consumers. That friction is real and it is the right friction — an expected value should not be trivially editable from inside a repository whose tests it governs. It also means the mitigations in 0002 (auto-bump internal dependencies, test against latest published) apply to the fixture package most of all.

A published dataset carries an implied warranty. A wrong `attested` value in a package presented as a citable reference is worse than a wrong value in a private test file, because others will build on it. Citations must be real and checked, and a value that cannot be sourced stays `unverified` rather than being quietly promoted to make a test meaningful.

**Now has to be true elsewhere.** The fixture repository needs a loader example per language it claims to support, or the language-agnostic claim is decoration. `maya-fixtures` gains the release step. `maya-plan` and `maya-fleet` reference the fixture package by version rather than by path. The dataset's own CI must validate its schema and assert that every record has a provenance and, where `attested`, a citation — the one place where automated checking of the citations themselves is possible.
